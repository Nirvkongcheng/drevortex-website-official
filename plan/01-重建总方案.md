# 官网重建总方案

## 1. 项目目标

本次项目不是对旧静态站做修补，而是基于全新技术栈重建一个可长期维护、可持续迭代、具备真实数据链路的高端企业级官网系统。

目标同时满足以下四点：

1. 保留旧站全部页面、主要布局、打开观感、核心视觉记忆点与关键动画感受。
2. 前端切换到 React 体系，结构组件化，状态可控，便于后续维护。
3. 增加后端与数据库，形成真实内容管理与留资链路。
4. 达到企业级官网标准：SEO、性能、可维护性、安全性、可扩展性都要成立。

## 1.1 非协商基线

- 旧站副本不是参考素材，而是新站的唯一视觉基线。
- 新站打开后的第一观感必须与旧副本保持一致，不能出现“重新设计”“重新编排”或“只保留神似”的情况。
- 所有公开页面都必须按旧副本逐页、逐段、逐层复刻，技术栈升级只允许改变实现方式，不允许改变最终呈现。
- 动效允许做性能优化和状态治理，但最终观感必须大于等于旧站。
- 如果新实现与旧副本在布局、层级、节奏、文案、视觉氛围上出现明显偏离，应视为不合格实现。

## 2. 设计与工程原则

### 2.1 视觉原则

- 保留旧站的科技感、克制感、电影感。
- 不改动页面大布局、模块顺序和打开后的主视觉节奏。
- 不把视觉高端感建立在无意义的堆特效上。
- 首页动效保留观感，但必须做性能重写。
- 当前阶段不允许自由发挥新的版式语言，必须先做到 1:1 高保真复刻，再考虑工程优化。

### 2.2 工程原则

- 先还原页面骨架，再逐段重建动效。
- 展示层不塞兜底逻辑。
- 组件职责单一，动画逻辑与数据逻辑分层。
- 内容配置、案例、站点设置进入数据库或受控配置，不再散落在页面模板。
- API 先定义，再编码。

## 3. 推荐技术栈

## 3.1 总体选型

- 前端站点：`Next.js 15 + React 19 + TypeScript`
- 样式系统：`Tailwind CSS 4 + CSS Variables + CSS Modules`
- 动画层：`Motion` 负责通用入场与状态动画，`GSAP` 仅用于首页复杂时间轴
- 数据请求：`TanStack Query`
- 表单：`React Hook Form + Zod`
- 状态管理：`Zustand`
- 后端：`NestJS 11 + TypeScript`
- ORM：`Prisma`
- 数据库：`PostgreSQL 16`
- 鉴权：`JWT + HttpOnly Cookie`，只面向内部管理后台
- 文件管理：首期本地对象目录抽象，二期可切换云对象存储
- 包管理与仓库形态：`pnpm workspace` 单仓多应用

## 3.2 选型理由

### 前端为什么不用纯 React SPA

- 企业官网需要 SEO、首屏性能、元信息控制与可预渲染能力。
- `Next.js` 属于 React 技术栈，能同时满足 React 组件化与 SSR/SSG 需求。

### 为什么不是旧式前后端模板站

- 旧站核心问题就是表现层、结构层、数据层混在一起，后续不可维护。
- 新项目必须从一开始就拆出前端、API、数据库边界。

### 为什么保留独立后端

- 官网后续一定会涉及真实留资、案例管理、内容配置、后台账号与审计。
- 单独 API 服务比把所有逻辑塞进前端框架更利于长期演进。

```text
  apps/

    api/                 # 后端服务，NestJS
  packages/
    ui/                  # 通用 UI 与站点组件
    config/              # ESLint、TS、Prettier、Tailwind 等共享配置

    nginx/               # 反向代理配置
  docs/
  plan/
```

## 6. 页面重建策略

### 6.1 首页策略

首页按“旧站结构 1:1 拆解 + 动画分层重写”执行，不允许保留巨型脚本，也不允许自行改造旧站模块顺序和主要视觉编排。

拆分为：

- `Header`
- `IntroSequence`
- `HeroStage`
- `ImpactBridge`
- `FlipShowcase`
- `ServiceArc`
- `FeaturedCases`
- `StickyConsultCTA`
- `Footer`

动画分为：

- 首屏时间轴动画
- 滚动触发动画
- hover 微交互
- 主题切换状态动画

### 6.2 子页策略

- 子页共用统一 Hero 组件、Section 容器、卡片组件、Reveal 动画组件，但外观、结构和内容必须先与旧副本逐页对齐。
- 各子页只允许在实现层去重，不允许在表现层擅自重构。

### 6.3 联系页策略

- 联系页表单必须接入真实 API。
- 验证码逻辑首期不做短信发送伪装，改为真实可用方案：
  - 首期推荐：表单提交 + 邮件/后台留资，不做短信验证码
  - 二期可接入短信服务

## 7. 数据化策略

### 7.1 首期进入数据库的数据

- 站点基础设置
- 导航项
- 首页模块文案与统计数字
- 关于页文案
- 服务分类与服务条目
- 案例分类与案例条目
- 联系留资记录
- 后台管理员账号

### 7.2 首期仍允许受控本地配置的数据

- 极少数纯装饰性动效参数
- 首页动画时间轴参数
- 非业务型常量

## 8. 设计系统方案

### 8.1 设计 token

统一抽出以下 token：

- 颜色
- 背景层级
- 文字层级
- 边框透明度
- 阴影
- 圆角
- 间距
- 容器宽度
- 断点
- 动画时长
- 动画缓动
- z-index 层级

### 8.2 组件层级

- 基础层：按钮、标签、标题、容器、分隔线、图标包装
- 组合层：导航、Hero、卡片、数字统计、案例卡、服务卡、表单项
- 页面层：首页区块、关于页区块、服务页区块、案例页区块、联系页区块

## 9. 性能目标

- 首页首屏不再同时启动全部动画。
- 首屏关键资源尽量控制在必要范围内。
- 桌面端 Lighthouse 目标：
  - Performance >= 90
  - Accessibility >= 95
  - Best Practices >= 95
  - SEO >= 95
- 核心 Web Vitals 目标：
  - LCP < 2.5s
  - CLS < 0.1
  - INP < 200ms

## 10. 安全目标

- 管理后台鉴权与公开官网彻底隔离。
- 后端接口做参数校验、限流、日志审计。
- 联系表单做基础防刷与来源校验。
- 敏感配置仅存在服务端环境变量。
- 图片与文件上传做白名单校验。

## 11. 实施边界

### 本次首期必须完成

- 5 个公开页面按旧副本 1:1 高保真重建
- 真实后端与 PostgreSQL
- 真实联系留资链路
- 基础后台内容管理能力
- SEO、性能、安全基线

### 本次首期不强制完成

- 多语言
- 短信验证码
- 完整 CMS 富文本系统
- 大规模媒体库工作流
- 多租户

## 12. 最终结论

本项目推荐采用“`Next.js 官网前端 + NestJS API + PostgreSQL + Prisma + pnpm workspace`”方案。

这是当前最稳的平衡点：

- 前端明确属于 React 体系
- 具备企业官网所需 SEO 与性能能力
- 有独立后端与数据库
- 能在不破坏旧站表现的前提下，把结构、样式、交互与数据全部工程化重建
